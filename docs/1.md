# The plan review — what happened, what changed, and what is still open

*Written 2026-09-21, after the review closed and before milestone 0 opened. Nothing in this
document is a decision; it is the record of decisions other people made. If you are picking this
project up cold, read this first, then `PLAN.md`.*

---

## What this was

To Dew had a spec and a build plan and no Swift. `SPEC.md` is an 808-line product spec. `PLAN.md`
was a 151-line plan for getting from that spec to a tagged 1.0 with Claude Code writing the code,
one milestone per branch and pull request. The spec had been read carefully. The plan had not been
attacked.

So it was — by four agents, each given one lens and told to ignore the others:

- **spec coverage** — does every promise in `SPEC.md` land in some milestone, and can each
  milestone's "Done when" actually be settled by a person?
- **technical feasibility** — will the mechanisms the plan names do what the plan says they do,
  on macOS 26, with SwiftData and WidgetKit and a free developer account?
- **sequencing and risk** — is the order right, are the pull requests a size a person can review,
  and is the biggest risk retired early or last?
- **agent workability** — can an agent with no eyes and no memory of the last run execute a row
  of this plan without inventing things?

Their four reports are `review/01` through `review/04`, 2,980 lines between them. A fifth agent
then adjudicated: read all four, checked the claims it was unwilling to take on trust, resolved
the places two reviewers wanted incompatible things, and wrote `review/00-adjudication.md`. It
deliberately edited nothing. A sixth run rewrote `PLAN.md` from that adjudication. A seventh —
this one — wrote the spec-edit proposals and this document.

The numbers, for calibration: **77 findings — 48 accepted, 25 accepted with modification, 1
rejected outright, 3 sent to the human as product decisions.** `PLAN.md` went from **151 lines to
355**. Its ten milestones became **ten milestones and twenty pull requests**, because seven of the
ten were between one and a half and four times the plan's own size budget and one of them held
roughly three thousand lines of production code in a single table cell.

Only one finding was rejected outright. That is not a sign the reviewers were right about
everything; it is a sign they were all pointing at real problems, and that the judgment lived in
the twenty-five modifications and in what got refused (see *Scope that was deliberately rejected*,
below).

## What was actually wrong

Five things, and the fifth is the one that hid the other four.

**The logical date was computed wrong.** `SPEC.md` says: subtract the rollover offset — six hours
— then take the calendar date. Do that across a daylight-saving transition and you land an hour
off in both directions. You neither skip nor duplicate a day, which is why the spec's own DST
acceptance row passes; the defect survives the test written to catch it. The fix is to read the
wall-clock hour and subtract a *day* when it is before the rollover time, never to do absolute-time
arithmetic on a `Date`. The arithmetic was checked by hand during adjudication rather than taken on
trust. `logicalDate` is the one function in this app that everything else depends on: the list, the
history, the streak, the widget, the notifications.

**`RecurrenceRule` did not compile.** It declared `weekdays` twice. Nobody noticed because nobody
had typed it into a compiler.

**Two comforting sentences were false.** "Rollover runs in one transaction" describes something
SwiftData does not offer — `ModelContext.transaction(_:)` does not roll back on error. And "all
writes go through one store actor so the app and the widget never conflict" is not a property an
actor has: an actor serialises one process. The widget is a second process. Both sentences read as
safety guarantees and neither was one.

**Scope the spec requires was in no milestone at all.** Nothing stored the eighteen settings.
Nothing navigated between the five views. Nothing built the task detail that `Cmd I` was bound to
opening. Nothing built the update check. And nothing declared a SwiftData schema version — the one
item on this list that cannot be bought back later at any price, because SwiftData cannot
retroactively identify an unversioned store.

**And the false comfort.** The plan claimed that rendering every component under two themes and
diffing the snapshots would enforce the rule that no view contains a styling literal. It does not
and cannot: a snapshot baseline is recorded *from the code under test*, so a hard-coded `12` is
written into both baselines on the first run and passes forever. Worse, the plan's risk table then
listed that risk as retired — so nobody would ever build the thing that would actually retire it.
Enforcement is now a syntactic lint (`scripts/lint-theme.sh`, written in `2a`) plus a requirement
that the deliberately-ugly `TestTheme` differ from `SageLilyTheme` in *every* token group.
Snapshots were relabelled what they are: a regression gate.

A sixth finding worth keeping in mind, because it will bite during milestone 2: the `Theme`
protocol had no token for opacity, stroke width, shadow or line height, while the design direction
requires 45% opacity on done rows, a 1.5 pt checkbox border and a 1 pt hairline *in milestone 2's
own components*. The no-literals rule broke in the milestone that establishes it.

## The six decisions the human made

The adjudicator refused to settle six questions on the grounds that they change what the product
*is*, and an integrator is not entitled to do that. It put each one up as an either/or with a
recommendation. Here is what the human chose. **All six are the human's calls, not the review's.**

**D1 — the widget.** *Chosen: pre-agree the kill clause.* A widget is an app extension, and an
extension may open a shared App Group container only under a Mac App Store deployment, a
Team-ID-prefixed identifier, or an embedded provisioning profile. This project has a free Personal
Team and ships an ad-hoc signed zip. Whether the *local* free-Personal-Team case works is untested.
So the widget moved from milestone 7 to **milestone 4**, directly after live rollover, and
`PLAN.md` now carries a signed-off clause: if the milestone 0 spike says no, milestone 4 is deleted
and the spec's widget section is struck, in the milestone 0 pull request. The human agreed in
advance to possibly losing a spec'd feature, in exchange for the project's only milestone-scale
binary risk being retired before roughly 5,800 lines of unrelated work are built on top of it.

**D2 — "Dynamic text size is supported."** *Chosen: spike it, and default to dropping the claim.*
macOS has no Dynamic Type for third-party apps; `UIFontMetrics` is iOS-only and
`Font.custom(_:size:relativeTo:)` compiles with nothing to scale against. Whether macOS 26's
Accessibility ▸ Display text size control moves anything is genuinely unknown and needs a human at
a screen — that is spike S6. Unless it comes back positive, the app ships a fixed type scale and
`SPEC.md:452` is amended. Either way the decision is made in `2a`, **before any component is
written**, because a scale factor changes the `Theme` protocol's shape and deciding it late means
editing every component and re-recording every baseline.

**D3 — does an absence break a streak?** *Chosen: yes, it breaks.* **This went against the
adjudicator's recommendation, deliberately.** The adjudicator argued for treating a day the app was
never opened on as neutral and skipping it — come back from four days away and your streak
survives. The human chose the opposite: a day that had tasks and no completion is a failure,
including a day nobody opened the app. Four days away is four failures and the streak starts again.
The streak measures days finished, not days visited. It is recorded as settled in `PLAN.md` §2 and
queued for `SPEC.md`, and it is not re-opened.

**D4 — the wallpaper token has no dark value.** *Chosen: record that it is light-only.* The
wallpaper is a light-scheme decoration; the dark scheme uses flat `background`. What a dark
radial-gradient ground should look like is a milestone 8 question, not a today question.

**D5 — the pink star sticker.** *Chosen: neither option offered.* `design/theme-sage-lily.md` says
`star-pink.png` is "used on the About screen only", which is simply false — there is no About
screen in `SPEC.md` and none is being built. The adjudicator offered two ways out: add a small
About window, or drop the star from the token file. **The human rejected both** and placed the star
in the **`DayHeader` component, to the left of the greeting line**, in every state. Its size, offset
and dark-scheme treatment are deliberately *not* specified: they are read off `design/mockups/today.png`
during the milestone `2b` screenshot round. If you are building `2b`, do not guess them.

**D6 — the Dock icon reflecting day state.** *Chosen: cut for 1.0.* It was a stretch goal routed to
"decided with the visual design", and the visual design milestone did not mention it. It is cut,
and — the point of the decision — it is being *recorded* in the spec's answered-questions table, so
the next reader does not re-open it.

## What is still open

**Seven claims entered `PLAN.md` as open questions with a named spike, not as assertions.** This is
the part most likely to get quietly lost, because a spike that nobody runs looks exactly like a
decision that was already made. They are laid out in `review/00-adjudication.md` §5, and each has a
decision record it must produce in milestone 0:

1. Whether a widget can open an App Group container under a free Personal Team with a
   Team-ID-prefixed identifier (`docs/m0-signing.md`, E1). What *is* certain and is asserted: the
   identifier must be Team-ID-prefixed, denial to an extension is silent, and CI's ad-hoc build
   cannot satisfy the rule.
2. Whether a SwiftUI `@Query` reliably observes a save made on the store actor's context
   (`docs/m0-readpath.md`). The Today view in `2c` is written against whichever answer comes back.
   What is certain either way: `@Model` is not `Sendable` and never crosses the actor boundary.
3. Whether macOS 26's text-size control moves a third-party app at all (`docs/m0-textsize.md`).
4. Whether a single `ModelContext.save()` is atomic across a crash (`docs/m0-durability.md`). The
   *design* — scratch context, autosave off, one save, rollback on error — is right under either
   answer and is asserted; the guarantee is verified, not claimed.
5. Whether notification authorization and `SMAppService.register()` work for an ad-hoc build
   outside `/Applications` (`docs/m0-freesigning.md`). Row `7b` ships fallback affordances **only
   if** the spike records a failure; no work is budgeted for a failure nobody has observed.
6. Which widget rendering modes the Mac desktop actually produces. The plan requires legibility in
   both of them and has the widget PR record which values it saw, rather than naming them up front.
7. Whether any shared location exists that the app can write and the extension can read. The
   milestone 0 spike answers this as an explicit line, which is what closes the
   "is there a snapshot-file fallback?" argument by evidence instead of by reasoning.

**And one structural thing is still open: milestone 4 may be deleted outright.** If spike E1 comes
back false, the widget is gone from every install path — not merely from the prebuilt zip, because
a sandboxed extension with no group container has no shared path to read, so there is no
snapshot-file consolation and no source-build consolation either. That deletion is pre-approved
(D1) and happens in the milestone 0 pull request.

## Scope that was deliberately rejected

The four reviewers, each optimising one lens, collectively proposed a 14-rule lint script, a
token-declaring preview catalog, a resolver-indirection rewrite of the theme layer, two synthetic
probe themes, a scripted screenshot harness, fifteen CI gates, twenty-one pull requests and a
three-page prompt library — for a free, local-only, single-developer hobby app that has not yet
compiled a line of Swift. Most of it is individually defensible. Together it is process built on
speculation before a single view exists.

`review/00-adjudication.md` §7 refuses seven pieces of it, with reasons. **If you find yourself
about to add one of these back, read §7 first — the case against it is already written, and it is
not "we forgot".**

1. **The fifteen-gate CI set, cut to seven.** Kept: core tests, UI tests, coverage on the two named
   files, the theme lint, an `xcodebuild` of the app and widget (the one genuinely missing gate —
   SwiftPM never compiles what ships), the no-network grep, and the release zip actually launching.
   XCUITest smoke runs nightly and on tags, not on every PR, because a flaky required check is how
   gates get disabled — and then all of them are.
2. **The token-contract machinery** — a recording theme, per-component declared token sets, a
   sentinel palette and metric-bump probes. The diagnosis behind it was accepted; the cure requires
   restructuring every token into a computed property over a resolver closure before a single view
   exists, and the allowlist it demands decays into exemptions by milestone 5. The lint catches the
   same leaks syntactically. If the lint proves insufficient during milestone 2, this is still
   available — and by then there will be evidence for it.
3. **`scripts/shots.sh` as specified.** The *fixtures* were kept and are load-bearing:
   `-ToDewFixture <name>` and `-ToDewNow <ISO-8601>`, debug-only, landing in `2c`. Without them the
   states that break layouts are the states nobody ever looks at. Rejected: the capture apparatus
   around them — osascript appearance toggling, per-milestone shot lists of twenty-plus files,
   contact sheets, a manifest attributing a token to each frame, and a formal verdict protocol with
   a reserved word for "unjudgeable".
4. **Fifty-five lines of prompt library as `PLAN.md` §5.** The substance was taken at about
   twenty-eight lines. Most of the remainder restates `CLAUDE.md`, which Claude Code reads on every
   run anyway, and duplicating rules across two files is how they drift.
5. **The twenty-first pull request, and an accessibility clause repeated in nine cells.** The
   widget is one row, not two: it is the row most likely to be cut wholesale, so splitting it to
   make half of it separately cuttable is a distinction without a difference. The accessibility
   rule is stated once above the table.
6. **Pre-writing the whole verification apparatus in milestone 0.** Every tool goes into the
   milestone that first needs it: the lint in `2a`, the fixtures in `2c`, the coverage gate in
   `1b`. Milestone 0 already carries six spikes, a second Mac and two wall-clock waits; it is the
   node most likely to be deferred, and deferring it is the most expensive thing that can happen
   here.
7. **The adjudicator deciding D1–D6 itself.** Six findings proposed changing what the product is.
   Surfacing those is a reviewer's job; settling them is not.

## How to use what is here

**`PLAN.md` is the working document.** Twenty rows, one per pull request. Each cell is a list of
gates, not features: every clause names the command that settles it or the numbered screenshot that
shows it. A clause naming neither is a bug in the plan — report it rather than interpreting it.
§3.1 is the exit checklist that opens every PR body, and §5 is the preamble you give Claude Code,
with one of three addenda depending on whether the row is logic, ends on screen, or touches things
no test can reach.

**`review/00-adjudication.md` is the appeal court.** When you disagree with something in `PLAN.md`,
look it up there before changing it. All 77 findings are in its §3 with a verdict and a reason; §4
records eleven places where two reviewers wanted incompatible things and which one won and why; §5
is the seven uncertain claims; §7 is the rejected scope. Most "wait, why is it like that?" questions
are answered in one of those five sections. `review/01`–`review/04` hold the detail behind any
individual finding, including the evidence and sources.

**`review/05-spec-edits.md` is a queue, not a changelog.** It holds proposed edits to `SPEC.md` and
one to `design/theme-sage-lily.md`, each with the exact current text, the exact replacement, a
rationale, and whether it is unconditional or gated on a spike result. **None of them has been
applied.** `SPEC.md` is the project's source of truth and `CLAUDE.md` requires that interpretations
of it be *proposed*; the human approves them item by item and a later run applies the ones marked
yes. Two of them cannot be applied at all until milestone 0 reports: the type-scale edit waits on
spike S6, and the widget strike waits on spike E1 and is applied only if E1 fails. Until that file
is empty, assume `SPEC.md` still says the old thing — including the daylight-saving arithmetic and
the frozen notification trigger, both of which `PLAN.md` already corrects. Where the two disagree
today, `PLAN.md` is the one that has been through this review.

**One habit worth keeping.** `docs/interpretations.md` is where an agent records any place it had
to interpret `SPEC.md`, in the milestone where it happened, and proposes the spec edit in the same
pull request. An empty interpretations file on a spec this size is a claim to check, not a good
sign.
